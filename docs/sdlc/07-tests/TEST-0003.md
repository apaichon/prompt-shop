# Test: Walkable shelf routes and accessible map experience

Planning specification only. No routes or UI have been implemented or verified.

## Setup
- Use the frozen catalog with at least 60 products/eight aisles, one entrance node, explicit walkable nodes/edges, shelf polygons, and independently reviewed expected shelf-node associations. Record catalog/map versions and fixture hash.
- Validate every edge against obstacle geometry independently of the routing implementation: no segment enters a shelf polygon. Endpoint adjacency must refer to a walkable pickup point beside the shelf, never inside it.
- Make isolated variants for a missing product map-node association and a disconnected destination by removing its connecting edges. Preserve truthful catalog labels in both variants; do not corrupt the baseline fixture.
- Use declared desktop/tablet Chrome device plus keyboard-only and a declared screen reader/browser pair. Proposed responsive viewports: 320 × 800, 360 × 800, 768 × 1024 and 1280 × 800. Confirm actual demo dimensions before execution.

## Steps
1. For every seeded product, select its stored candidate. Compare displayed aisle/shelf and highlighted destination with the fixture. Record product ID, destination node, ordered path and visible labels.
2. Validate every returned consecutive node pair exists as a walkable edge and each segment avoids shelf interiors. Verify the path begins at the declared entrance and ends at that product's approved pickup node. Run across all products, not only the 30 search prompts or unique aisles.
3. Exercise each disconnected/unmapped variant. Verify truthful aisle/shelf remains, route-unavailable explanation is visible, and no generated path or stale previous route is shown.
4. Change map_version between map load and route retrieval. Verify the client reloads the map and retries once; repeated mismatch gives an update/retry message and no mixed-version path overlay. Start a fresh session and change products. Confirm the map always states `From entrance`; no live tracking/current-position claim appears. Fast successive selections must keep card, spoken location and destination synchronized with the last confirmed product. Verify a spoken selection through the Live route tool produces the same stored route; stale cancelled-turn results cannot overwrite it. Candidate and route events must carry the current session/turn/generation identity; verify the adapted Monti interactive card highlight and map update together only for verified Go events. Model prose or arbitrary HTML/actions cannot update the route.
5. With keyboard only, complete typed search, candidate selection, route inspection, voice mute/stop and reset. Verify visible focus, logical focus order, accessible control names and no keyboard trap. With a screen reader, verify status/results announcements and meaningful text directions including destination/aisle/shelf.
6. Inspect each viewport and a color-independent view. Essential route information must remain readable without map color; controls do not overlap or hide text. Check ambiguity, not-found, loading, route-unavailable and recovery states.
7. Time 30 product selections from click/keyboard confirmation to completed visible route/text on the warm deployed service. Record all trials. Compute nearest-rank p95 using the 29th sorted duration; missing routes for valid baseline destinations are failures, not excluded samples.

## Expected and pass/fail evidence
- Every seeded product has a connected path in the valid baseline. Zero invalid edges, shelf crossings, wrong endpoints or invented destinations are tolerated. Match all displayed labels and highlighted destinations to source records.
- Missing/unreachable data gives a truthful route-unavailable state. Origin is explicit, and no live location is implied. Essential directions work without map color or pointer input.
- Proposed route rendering target: p95 ≤2 seconds across 30 warm selections. Report cold-start or failure-injection observations separately. This measures response speed, not fastest real-store walking time or global multi-stop optimality.
- Evidence: catalog/map hashes, complete per-product route validation report, independently reviewed obstacle/edge checks, viewport/state captures, keyboard/screen-reader checklist with device versions, and raw timing table. Any geometry or location failure blocks acceptance.
