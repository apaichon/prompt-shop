# Deployment plan: English voice demo on GCP

This is a proposed runbook, not a deployment record. No resources, image, release branch, tag, URL or successful test run are claimed. `v0.1.0` is a planned version; populate actual source revision, image digest, Cloud Run revision and `git_tag` only after their creation through the project Git workflow.

## Target and gates

Deploy the working English prototype by **16 October 2026**, with **17:00 Asia/Bangkok (UTC+7)** proposed as the acceptance cutoff. TASK-0005 proves the cloud path on 14 October; TASK-0006 supplies QA evidence; TASK-0008 promotes the final release on 16 October. Rehearse and package on 17 October; user submission is due 18 October.

One Cloud Run service revision contains **three immutable container images**: Go Fiber serves the compiled static SvelteKit portal, APIs and public WebSocket gateway; Python ADK owns native Gemini Live sessions; a private Laya sidecar performs required English intent classification. Customer `/` and protected `/backoffice` share the portal. Selected `monti-jarvis` browser audio, interactive shopping UI and bridge patterns are adapted; its entire runtime is not copied. Cloud SQL PostgreSQL persists the sample catalog independently of container restarts and is accessed only by Go. Required voice flow is browser PCM → Go gateway → **Python ADK → Gemini 3.8 Live**, with Laya classification and ADK read-only tool callbacks validated by Go before database/route access. Laya is mandatory under REQ-0006/TASK-0010; it is not silently removed if timing/resource gates fail. CPU PyTorch/model dependencies belong only in the Laya image; no GPU is assumed.

Propose one region for Cloud Run, Cloud SQL, Artifact Registry and builds where supported. `asia-southeast1` is a candidate near Bangkok, **not a Gemini endpoint or residency guarantee**. Use the Gemini Developer API initially with model ID `gemini-3.8-live`; its availability is documented, but actual account access, quota and billing still require proof. Do not assume Vertex AI has the same model or that Cloud Run ADC replaces the Developer API key. Record the chosen provider endpoint, cross-region processing implications and measured latency separately from the GCP hosting region. See the official [Gemini 3.8 Live model](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live).

The required stream is mono signed 16-bit little-endian PCM at 16 kHz into Live and PCM at 24 kHz back to the browser. **Only the Python ADK container receives the Gemini API key** and owns its provider WebSocket; neither Go nor the browser receives that key. See the [Live API transport/audio overview](https://ai.google.dev/gemini-api/docs/live-api). Source configurations still naming Gemini 2.5 must migrate explicitly to 3.8: remove unsupported thinking/affective settings, do not disable proactive audio, and declare catalog tools `BLOCKING` so location speech follows tool evidence. No silent older-model or separate STT/TTS fallback is permitted. Validate these setup differences against the [3.8 migration notes](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live).

Pin the actual Python, `google-adk`, `google-genai` and ASGI server versions in a resolved dependency lock during the feasibility task; no guessed compatible version is accepted. ADK must use its real bidirectional `Runner.run_live()`/`LiveRequestQueue` path rather than relying on a streaming-mode flag alone. Prove audio, blocking tool behavior and cancellation with that locked stack. See Google's [ADK Live configuration source](https://github.com/google/adk-docs/blob/main/docs/live/configuration.md) and [Python streaming guide](https://github.com/google/adk-docs/blob/main/docs/live/get-started/streaming-python.md).

Package only the selected English-root `convaiinnovations/laya` checkpoint, pinned to an actual Hugging Face commit and verified weight digest. Resolve exact Laya/CPU PyTorch/Transformers/tokenizer dependencies into a separate lock. Download and verify artifacts during the build, preserve required source/model notices, and run offline from bundled files; no first-request download or automatic multilingual checkpoint routing. The [publisher model card](https://huggingface.co/convaiinnovations/laya) identifies the English root and Apache-2.0 license; retain the exact pinned model card/license and review any dependency notices before distribution. Publisher benchmark latency is not evidence for this Cloud Run CPU allocation.

Only the allowlisted catalog lookup/route tool handlers in DES-0001 are exposed to Live. Server-side schema validation, store scoping, published-product state and database/map truth govern tool output. No admin mutation, arbitrary SQL, HTTP fetch or source-system business workflow is exposed as a model tool. A failed or rejected tool cannot authorize invented aisle/shelf speech or a route card; report bounded unavailability instead.

## Identities and secret handling

Use separate named identities; do not use project-wide Owner/Editor as runtime permissions.

| Identity | Proposed scope |
|---|---|
| Human/CI deployer | Cloud Run Developer, Artifact Registry Reader, and Service Account User on the intended runtime identity; scoped Cloud Build submission/inspection permissions for the three builds; administrator handles one-time API/IAM changes |
| Dedicated build service account | Scoped source read, image repository write and build-log write for the three-image pipeline; model artifacts fetched from the pinned approved source during build; no runtime database password, internal tokens or Gemini key |
| Revision runtime service account | Cloud SQL Client and Secret Manager accessor on required named secrets; database/admin secrets only in Go, Gemini key only in ADK, bridge token in Go+ADK, separate Laya token in ADK+Laya; no standalone speech API workload role |
| Migration/import job identity | Cloud SQL Client and access only to migration credentials; SQL DDL/upsert privileges; no speech/model access |
| Public-query database principal | SELECT on catalog/map only |
| Backoffice database principal | Narrow catalog INSERT/UPDATE, store-version update, audit append and session lifecycle rights; no DDL, DROP, catalog delete or unrestricted import privileges |
| Voice-ticket database principal | Narrow ticket issue/consume/expiry lifecycle rights; catalog tools use the read-only query principal; no catalog writes |

Verify effective identities rather than relying on a default service-account name. Build all three images in Cloud Build, store digests in Artifact Registry, and deploy together through a reviewed multi-container manifest. This supersedes single-image source deployment. Container deployment roles and sidecar configuration are documented in [deploying container images](https://cloud.google.com/run/docs/deploying#sidecars). The revision has shared identity/network: per-container secret injection is configuration separation, not a strong IAM boundary against a compromised sibling container.

Use Cloud Run's Cloud SQL connection integration and a bounded Go connection pool; select the documented authenticated connection route before provisioning. Proposed simple route is the integrated socket with Cloud SQL public IP and no broad authorized-network rule, subject to organization policy. If private-only connectivity is required, add VPC configuration to TASK-0005 and recheck schedule. Credentials live in Secret Manager, with explicit secret versions recorded per revision. No service-account keys, passwords or API keys in repository, image, SPA bundle, request URLs or logs. See [Cloud SQL connections from Cloud Run](https://cloud.google.com/sql/docs/postgres/connect-run).

Backoffice access is mandatory regardless of customer-demo access: keep the bcrypt admin password hash in Secret Manager. The server issues an opaque random session token, stores only its SHA-256 hash in PostgreSQL, and expires it after eight hours. Use the `__Host-maintainer` cookie with Secure, HttpOnly, SameSite=Strict and Path=/; logout revokes the database session and clears the cookie. Login checks the configured exact Origin; authenticated mutations additionally require a per-session `X-CSRF-Token` with constant-time comparison. Protect every catalog write on the server; hiding `/backoffice` is not authorization. Do not copy source-system credentials, default passwords or permissive development bypasses from the reference snapshot. TASK-0009 and TEST-0005 must prove product create/update, aliases and valid shelf assignment survive a revision change and that unauthenticated/forged writes are rejected.

## Multi-container lifecycle contract

| Process/listener | Reachability and responsibility |
|---|---|
| Go public listener `0.0.0.0:$PORT` (explicit ingress port 8080) | The only Cloud Run ingress; serves portal/API and authenticates `/ws/voice` |
| Python ADK listener `0.0.0.0:8001` | No Cloud Run ingress port mapping; Go uses `127.0.0.1:8001/live` with a Secret Manager bridge bearer token; `/healthz` contains no secret |
| Go tool listener `127.0.0.1:8002` | Only fixed `/internal/tools/search_catalog` and `/internal/tools/get_product_route`; active-session capability plus epoch and trusted ADK `classification_attempt_id`; capability delivered through authenticated bridge and revoked at socket end |
| Laya listener `0.0.0.0:8003` | No Cloud Run ingress mapping; ADK calls fixed `/classify` with `X-Internal-Token` from its separate shared secret; `/healthz` succeeds only after pinned model load and CPU warmup |

Choose sidecar all-interface binds for platform startup-probe reachability; this is a conservative choice, not a claim that loopback binds are forbidden. Public Fiber never proxies arbitrary private paths. Python has no SQL credentials or admin tool. Reject wrong bridge credentials, expired capabilities, mismatched epoch/session and arbitrary callback URLs. Only a trusted private ADK completion event registers a classification attempt, including explicit abstention; ADK waits for the matching Go registration ACK before dispatching a catalog callback; the model/browser cannot mint this authorization metadata.

Cloud Run supports same-instance localhost communication and only one exposed ingress. Configure startup order **Laya model-loaded probe → ADK import/config probe → Go**. ADK health does not call Laya, Go or Gemini, avoiding a dependency cycle; provider access is a separate paid smoke check. Give Laya an explicit measured startup budget and fail deployment if its fixed checkpoint cannot warm up in that budget. Startup ordering is documented in [container configuration](https://cloud.google.com/run/docs/configuring/services/containers); HTTP probe behavior is in [health checks](https://cloud.google.com/run/docs/configuring/healthchecks).

Laya accepts only the fixed intent schema and text length 1–300 characters; model/config/prompt/URL are not client-selectable. Run one inference at a time with queue capacity four, a 200 ms queue wait ceiling and total 1,200 ms deadline including queueing. No retry; timeout/overflow yields observable abstention under DES-0001, not a claimed inference success. Terminate/replace a stuck worker so a timed-out CPU inference cannot accumulate unseen work. Required normal-flow acceptance must execute real inference. TEST-0012 checks at least 36 correct of 40 frozen English intent cases plus timeout/overload/auth/resource behavior; failure blocks the required release scope.

Use explicit per-container CPU/memory limits. With request-based billing, sidecar CPU is available during startup/request processing; active browser WebSockets provide that request lifetime. Do not rely on background cleanup after requests disappear: cancel ADK queues/provider sockets before returning the final close. If essential background work is later introduced, review instance-based billing. See [sidecar CPU behavior](https://cloud.google.com/run/docs/deploying#sidecars).

All three processes must handle SIGTERM concurrently: refuse admission, stop browser/bridge streams, close ADK queues/provider connections, cancel/terminate Laya work and revoke capabilities. Do not assume a shutdown order. Cloud Run gives a 10-second window before SIGKILL; set an internal drain target below it and test abrupt sibling loss. See the [container runtime contract](https://cloud.google.com/run/docs/container-contract).

4. Run a single controlled migration/import job before traffic promotion; do not migrate concurrently on every app start. Use transactional, versioned migrations and a migration lock. Seed 60 products/eight aisles with stable IDs, aliases, shelf references and walkable map edges. Rerun proves idempotency. Reject invalid references atomically; record seed version/checksum and migration version, not credentials.
5. Prove **ADK + Gemini 3.8 + real Laya intent inference** on **13 October**, then deploy the three-container staging revision by **14 October 18:00**. Check startup, private auth, PCM, intent result, interactive shopping cards/routes, interruption and sibling failure. Source coupling, ADK compatibility and Laya CPU latency/memory are critical risks; a direct Gemini demo or mocked classifier does not satisfy the gate.
6. After QA gates, deploy the matched candidate image set without ordinary demo traffic where supported; test through the chosen access mechanism. Retain the first tested three-container revision for rollback once established.

Record actual release commit/tag, all image/model/dependency digests, bridge version, revision, secret versions, schema/seed versions, access configuration, timestamps and evidence. Keep the matching known good image set and compatible secrets.

Cloud Run supports revision traffic assignment and rollback; changes are not instantaneous and in-flight requests may finish on the earlier revision. Verify the serving revision after promotion. ## Demo access, capacity and cost

**Access is a review decision, not implied permission to publish.** Recommend controlled browser access for named demo reviewers. Use the access mechanism frozen in DES-0001 and prove it with a fresh browser session on 14 October; private Cloud Run IAM alone does not provide an ordinary shopper login page. If selecting IAP, first prove account eligibility/setup and browser flow; do not add an unproven integration on release day. If selecting a public demo, explicitly authorize unauthenticated reachability, retain API abuse limits and set a removal date. See [Cloud Run access control](https://cloud.google.com/run/docs/securing/managing-access) and [IAP for Cloud Run](https://cloud.google.com/iap/docs/enabling-cloud-run).

Proposed initial allocation is **Go: 1 vCPU/512 MiB; ADK: 1 vCPU/512 MiB; Laya: 2 vCPU/4 GiB**, totaling **4 vCPU/5 GiB per instance**. These are unmeasured starting values, not proof of sufficiency. Verify regional CPU quota, supported allocation, model startup/RSS peaks, queue usage, inference latency and cost. Retain concurrency 10, maximum 2 instances, minimum 0 off-demo and optionally 1 at rehearsal if affordable; nominal two-instance capacity costs must include every sidecar, with overlap headroom. Cap Go SQL pools at 5 connections/instance; ADK/Laya have none. Qualify five-user load on 14 October; resource or latency failure requires a reviewed correction, not automatic Laya removal. Cloud Run timeout **360 seconds**; session **300 seconds from ready**, idle **60 seconds**, setup **30 seconds**. HTTP/tool/Laya deadlines remain separately bounded.

Before upgrading `/ws/voice`, atomically consume the single-use, 30-second `__Host-voice-ticket` issued by `POST /api/voice/sessions`, check exact allowed Origin and verify available application capacity. Cookie is Secure/HttpOnly/SameSite=Strict; no credential in query strings. Allow at most four active Live sessions per instance, releasing the slot on every disconnect/setup failure. Two intended steady-state instances imply up to eight, **not a strict global cap** during rollout/transient scaling; record provider-account concurrency quota and any tighter service-wide admission decision before exposure. Ticket issuance is 5/minute/IP (burst 2); search/routes 60/minute/IP (burst 10); admin login 5/minute/IP (burst 2); admin writes 20/minute/session. Per-instance limits do not constitute global quotas.

Apply DES-0001 frame budgets: nominal 3,200-byte audio/100 ms, maximum 6,400-byte frame, input 40 KiB/second with 64 KiB burst, at most 10 MiB audio per session; control JSON ≤4 KiB and ≤10 messages/second. Bound both relay queues, cancel interrupted output and stale tool work, and close abusive or slow consumers. On disconnect release capture/playback and provider resources; explicit reconnect gets a fresh ticket and fresh provider session without replaying recorded turns. Verify these paths under quota rejection, network loss and revision changes.

Cloud Run WebSockets remain subject to request timeout and keep their instance active/billable while open. One established connection stays on its instance; reconnect can land elsewhere, so affinity cannot provide session recovery. Keep ticket state in PostgreSQL and do not require in-memory state on the next instance. Disable HTTP/2 end-to-end for this path. See [Cloud Run WebSocket guidance](https://cloud.google.com/run/docs/triggering/websockets).

Maximum instances reduces scaling exposure but is not an absolute spending guarantee or a sufficient database connection bound during transitions. Check service and revision settings together. See [maximum instances](https://cloud.google.com/run/docs/configuring/max-instances). Budget alerts notify; **they do not cap charges**. Review SQL baseline cost, active WebSocket runtime, Gemini audio/context usage and session quotas, build minutes, artifacts and logging; propose 50/80/100% budget alerts with a named recipient. Measure per-demo session usage; closing the browser/session must close its provider connection. Provider quotas, bounded sessions and an operator action that refuses new voice sessions and closes existing sessions complement monitoring. See [budget alerts](https://cloud.google.com/billing/docs/how-to/budgets).

## Acceptance and rollback

TEST-0004 must record HTTPS/browser microphone behavior; readiness; 60-product persistence after revision restart; native voice, typed fallback, ambiguity, unknown item and route smoke; secret/log inspection; bounded recovery; and rollback timing. Across 30 warm English turns measure from user utterance end to **first actionable spoken response p95 ≤5 seconds** and **grounded visible card p95 ≤8 seconds**; a filler acknowledgment does not meet the speech target. Typed search and route rendering have p95 ≤2 seconds over 30 trials. Record cold/session-setup timing separately, device/network/region and concurrent load. Correct catalog item must appear in the first three for at least 27/30 supported prompts; no fabricated shelf location is acceptable. Include interruption, ticket replay/wrong Origin, session expiry, quota rejection and fresh-session reconnect.

Service health and voice availability are separate: Go `/healthz` checks its process; `/readyz` checks database/seed and private ADK/Laya health with 250 ms deadline per sidecar, reporting nonsecret capability/configuration state. ADK `/healthz` checks imports/config/listener without Go/provider; Laya health requires fixed checkpoint load/warmup. Missing Gemini configuration or sidecar failure exposes unavailability while typed lookup may remain usable after startup. No probe claims a provider handshake or classification accuracy. Acceptance requires ADK audio/tools and real Laya inference. Never call the paid model on every probe or silently bypass a required component.

Rollback triggers: broken core smoke, wrong stored location, repeated 5xx/DB failures, secret exposure or acceptance regression. Restore **matching Go/ADK/Laya images, checkpoint, bridge protocol and secrets**, drain old sessions, then prove typed and fresh ADK/Gemini voice routes with real Laya inference. Existing sockets may stay on the old revision until closed; new ones must prove the target. Target recovery **15 minutes**, measured in rehearsal. Keep additive compatible schema changes; no destructive reseed/removal. Revision rollback does not undo migration. For catalog/schema corruption, stop imports, preserve evidence and restore a verified backup to a separate recovery database or apply reviewed forward repair; this may exceed 15 minutes. Retain seed/migration artifacts and pre-migration backup.

After service recovery, correct source through the documented revert/hotfix workflow; never rewrite a release tag. Create a real operations record only if an event occurs. Until actual deployment, this artifact remains `proposed`.
